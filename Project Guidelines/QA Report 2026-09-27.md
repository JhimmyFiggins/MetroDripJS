# QA Report: 2026-09-27

Final validation: 2026-09-28 UTC. Initial discovery and baseline runs: 2026-09-27.

## 1. Executive Summary

**Release recommendation: HOLD.** This is a bounded local QA and remediation pass, not certification of the entire product. Staff-console authentication remains simulated, automatic outbox delivery/reconciliation is absent, and native-device, PostgreSQL concurrency, provider, and production-edge verification are unavailable. Earlier repository claims of complete verification or zero blockers are superseded by this report.

Scope: active `services/*` Django applications, Python gateway, static Admin/Merchant consoles, and current mobile source contracts. The legacy `metrodrip_backend` application is not the tested deployment target and must not be treated as verified or exposed based on this report.

Environment: Windows; Python 3.15.0b2, Django 5.2.16, DRF 3.18.1; Node 24.16.0; Playwright Chromium. Python is a prerelease runtime, not a supported production-version certification. Tests use in-memory or disposable SQLite databases. Browser APIs are explicitly mocked; external resources are blocked. No existing application database is intentionally mutated, no real payment/provider operation is performed, and no commit or deployment is made.

**Executed results:** 240/240 automated tests passed (100% of that executed set, zero remaining automated failures); 64/64 browser layout cases passed; 5/5 isolated API integration phases passed. The coverage matrix still contains four FAIL and six BLOCKED groups. These counts are not an overall product coverage percentage. Subtests, HTTP assertions, viewport cases and grouped matrix rows have different denominators.

Automated breakdown: Identity 19, Catalog 21, Orders 28, Fulfillment 18, Content 19, Gateway 17, harness safety 4, client/dev-server tests 114. The client suite includes mocked-module tests, source invariants, one extracted real submission-handler execution test and live HTTP tests against a temporary copy of the web server. None of those are rendered native-device tests.

## 4. Residual Risk & Deployment Recommendations

1. Do not deploy as release-ready. Resolve real staff sessions and open event/reconciliation defects, then rerun live browser-to-API workflows against disposable databases.
2. SQLite rollback and sequential replay are not proof of PostgreSQL lock correctness or global ACID. This architecture is a saga with local transactions and cross-service eventual consistency, not a distributed ACID transaction. Test simultaneous first-order creation, duplicate keys, stock contention and crash/restart boundaries on PostgreSQL.
3. Same-customer reuse of an idempotency key with a different payload is not fingerprint-validated server-side. Order-number allocation still derives the next ID from the latest row. Both require explicit concurrency and conflict-policy work. Mobile attempt keys survive retries of the same in-memory draft, not process restart or reconstructed navigation state; durable retry recovery is still required.
4. Restore dependencies under the project's lockfile and compile/render mobile code. Use real Android and iOS devices for token lifecycle, accessibility, navigation, offline/reconnect and double-submission checks. Provider mocks do not establish real payment, email or push delivery.
5. Keep the legacy monolith and internal service ports private. Production secret provisioning, debug/host/CORS settings, TLS, credential rotation, rate limits and Nginx policy require separate deployment validation. No credentials were rotated in this pass.
6. Monitor oldest pending outbox age, pending-stock duration, release-pending holds, duplicate-key conflicts, inventory discrepancies, failed authorization, checkout error rate and dependency health. Redact tokens, payment details and customer addresses. Define alert thresholds from measured service objectives rather than inventing capacity claims.
7. Browser checks cover Chromium only and fallback fonts. Full focus semantics, screen readers, measured contrast, 200% zoom, localization, Safari and Firefox remain unverified. Node/source checks are not substitutes for rendered native tests.

Evidence ownership: this report and current automated test outputs supersede historical readiness claims in other project records. No claim of zero future regressions, complete security, or exhaustive UI coverage is made.
